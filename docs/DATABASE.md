# Database design

Status: approved in Part 5 and implemented in Part 6.

The machine-readable contract is `database-schema.json`.

## Storage

- Engine: SQLite
- Container path: `/app/data/project_management.db`
- Persistence: the existing `pm-data` Docker volume mounts `/app/data`
- IDs: UUIDv7 strings generated by the backend
- Timestamps: UTC ISO-8601 strings
- Ordering: zero-based contiguous integer positions

SQLite starts each connection with foreign keys enabled, WAL journaling, and a
five-second busy timeout.

## Relationships

```text
users
  └── boards
        ├── board_columns
        │     └── cards
        └── chat_messages
```

A user may own multiple boards in the schema. The MVP API will expose only the
first board for the signed-in user. This keeps the MVP simple without requiring
a future schema rewrite.

Deleting a user cascades through their boards, columns, cards, and chat history.
Deleting a column cascades through its cards.

## Ownership

Every board lookup begins with the authenticated username and joins through
`users.id` to `boards.user_id`. Column, card, and chat operations are accepted
only after resolving that ownership path. Client-supplied user IDs are never
trusted.

## Ordering and transactions

Columns are unique by `(board_id, position)`. Cards are unique by
`(column_id, position)`.

Create, delete, reorder, and cross-column move operations run in one immediate
transaction:

1. Resolve and verify board ownership.
2. Load the affected ordered rows.
3. Calculate the new zero-based order.
4. Move affected rows to temporary high positions when necessary to avoid
   transient unique constraint collisions.
5. Write final positions and increment `boards.version`.
6. Commit; otherwise roll back the complete change.

The board version provides optimistic concurrency and lets the backend reject
an AI proposal if the board changed after the proposal was created.

## AI conversation data

Chat history is board-scoped and ordered by creation time plus ID.

An assistant message may contain a validated JSON array of proposed operations,
its source board version, and one status:

- `pending`
- `confirmed`
- `rejected`
- `stale`

User messages and text-only assistant messages cannot contain proposal fields.
Confirmation rechecks ownership and board version, then applies all proposed
operations in one transaction.

## Initialization and migrations

On startup, the backend:

1. Create `/app/data` when needed.
2. Open the SQLite file and apply required pragmas.
3. Create `schema_migrations` if absent.
4. Apply numbered SQL migrations in order inside transactions.
5. Seed the MVP user, their board, fixed columns, and demo cards only when the
   user does not already exist.

Migration files are immutable after release. Each applied version is recorded
in `schema_migrations`; startup is idempotent.

## Backup and reset

Stop the application before a manual file backup:

```powershell
.\scripts\stop.ps1
docker run --rm -v project-management-mvp_pm-data:/data -v ${PWD}:/backup alpine `
  cp /data/project_management.db /backup/project_management.db.backup
```

The normal stop scripts preserve the volume. A full local reset is explicit:

```powershell
docker compose down --volumes
```

The reset command deletes all future board and chat data and is intentionally
not included in the stop scripts.
